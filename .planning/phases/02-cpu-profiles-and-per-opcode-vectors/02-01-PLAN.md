## Phase Goal (user story)

**As a** developer, **I want to** have the 65C02-class CPU execute under data-defined Lynx I and Lynx II profiles, proven by pinned per-opcode vectors, **so that** later device phases build on a CPU whose behaviour is checked per profile without either profile being adopted as baseline.

<objective>
Build the cycle-stepped CPU and its profile tables as a pure core unit, proven white-box on a flat test bus, before the machine uses it (the machine keeps the Phase 1 skeleton step until plan 02-09).

Purpose: CONTEXT "CPU structure and the bus-cycle interface" (cycle-stepped CPU that posts accesses as data, no function pointers, guard include gate) and "Profiles: ids, names, semantics" / "Profile data shape" (one X-macro `.def`, `[2][256]` integer-only table, `none` = agreement of both tables). This plan carries the architecture risk (RESEARCH AD-01) first, on the agent's best context.
Output: `core/cpu.h`, `core/cpu.c`, `core/cpu_profile.def`, `core/cpu_profile.c`, the flat test bus, `lynx-test-cpu` and five inventory rows.

Estimate note: the projection (about 1.1x the per-plan budget, uncalibrated, sample_count 0) is accepted per the CONTEXT amendment from plan check iteration 1: the executor gets a fresh context, and if it nears its limit it splits at a task commit boundary and records that in the SUMMARY. Do not re-slice or renumber.

Tracer note: the leading task is the thinnest slice through every layer this plan touches (profile data, decode, posted request, test-side grant/perform/log, completion, CTest registration, exact inventory, claim hash). The machine/API/runner layers join at plan 02-09 because the golden re-baseline must be atomic (RESEARCH 9.3).
</objective>
