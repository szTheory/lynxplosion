## Phase Goal (user story)

**As a** developer, **I want to** have the 65C02-class CPU execute under data-defined Lynx I and Lynx II profiles, proven by pinned per-opcode vectors, **so that** later device phases build on a CPU whose behaviour is checked per profile without either profile being adopted as baseline.

<objective>
Switch the machine from the Phase 1 skeleton step to the real CPU and re-baseline Phase 1 on purpose, in one green boundary (CONTEXT "Re-baselining Phase 1 on purpose", "Public API, registers, snapshot", "CPU structure and the bus-cycle interface": budget semantics keep the Phase 1 invariant, UNDEFINED before the opcode, tick stamps, cost model; CONTEXT amendments: two new registers, payload 65,568 bytes).

Purpose: CPU-02 (per-instance profile selection), CPU-03 (tick-stamped bus cycles in the shipping machine) and CPU-04 (interrupt machinery reachable through the machine). Every user of the skeleton step, `LYNX__HALT_OPCODE`, the budget helper and snapshot format 1 changes here, because the golden and the claim cannot be disabled across plans (`policy.no_skip`).
Output: the switched core, format 2, rewritten API tests, det values, regenerated golden and re-pointed claim.

Re-baseline order (CONTEXT): vectors green (02-04..02-06), then the hand-derived program checks green (Task 2), then the golden regenerated (Task 3) with the reason in the commit.
</objective>
