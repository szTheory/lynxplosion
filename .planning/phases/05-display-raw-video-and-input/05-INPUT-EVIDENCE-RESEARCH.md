# Phase 5 input and fixture evidence

**Scope:** Logical input mapping and timeline sampling, an original tier-A input/frame fixture, public-consumer evidence, and the input-facing disposition of the `page-mode` run and Phase 4 timer mismatch. This is bounded planning research, not an implementation or a hardware-accuracy claim. Reviewed 2026-11-11.

## Input API approaches

| Option | Pros | Cons | Complexity | Recommendation |
|---|---|---|---|---|
| Host-owned timestamped timeline; `lynx_input_set` replaces current logical levels at the machine's current guest tick | No core queue or retained caller pointer, constant-time input reads, host can hash the complete canonical timeline, composes with bounded `lynx_advance` and its half-open tick boundary | Host must advance exactly to each event and fail if the machine stops before it; replay cursor stays host-owned | Public API, Suzy bus read, machine state/digest, snapshot, runner/consumer and manifest; risk: caller mishandles an edge or loses replay position | Rec if deterministic replays and the existing allocation-free API boundary remain priorities |
| Core-owned queue of future `(tick, levels)` events | A single advance can cross input edges; core controls event ordering and the queue cursor is naturally visible to guest-time execution | Requires bounded capacity and a refusal rule, copies or owns all events, queue/cursor become snapshot state, makes reset/restore and run identity more complex | Public API, machine/scheduler, snapshot, digests, timeline parser, runner/consumer and manifest; risk: queue capacity, event-time overflow and snapshot mismatch | Rec if future callers need to advance across events without an event-stepping host |
| Replace levels only at frame or vblank boundaries | Simple host loop and a natural UI polling point | Drops valid mid-frame transitions, makes game polling frequency irrelevant, hides the sampled tick and cannot test exact event edges | Frame callback plus input and runner/consumer; risk: one-frame latency and incorrect CPU-visible reads | Rec only if a separate frontend convenience layer needs frame-rate input sampling |

**Rationale:** Use host-owned events and apply each event through a current-level setter after advancing to its guest tick. The public API already guarantees that a bounded advance does not start a CPU request due exactly at the exclusive target, so a timeline driver can stop at tick `T`, set the new levels, then resume; a CPU read granted at `T` sees the new levels. That avoids a core queue and gives an explicit, deterministic policy at an otherwise undocumented physical sampling edge. Keep the current levels in guest state and snapshots, and bind the full future timeline to the run manifest/digest so a restored run can resume with the same host-owned event sequence.

## Register mapping and semantics

The pinned cc65 source in the configured cc65 revision (`eebf54af545f4ae52f8489a2f6d4d5f93e7942d2`, `pins.txt`) identifies the Suzy input registers at `$FCB0` (`JOYSTICK`) and `$FCB1` (`SWITCHES`). Its `_suzy.h` names the joystick bits; `lynx.h` aliases `JOY_BTN_1` to logical A and `JOY_BTN_2` to logical B. These are suitable register/ABI evidence for the project fixture, not an independent hardware qualification.

| Logical level | Readback | Bit | Evidence note |
|---|---|---:|---|
| Up | `$FCB0` | `$80` | `JOYPAD_UP` |
| Down | `$FCB0` | `$40` | `JOYPAD_DOWN` |
| Left | `$FCB0` | `$20` | `JOYPAD_LEFT` |
| Right | `$FCB0` | `$10` | `JOYPAD_RIGHT` |
| Option 1 | `$FCB0` | `$08` | `BUTTON_OPTION1` |
| Option 2 | `$FCB0` | `$04` | `BUTTON_OPTION2` |
| B | `$FCB0` | `$02` | `BUTTON_INNER`; `lynx.h` maps button 2 to B |
| A | `$FCB0` | `$01` | `BUTTON_OUTER`; `lynx.h` maps button 1 to A |
| Pause | `$FCB1` | `$01` | `BUTTON_PAUSE` |

Treat each logical input as an independent held level. Compose `$FCB0` from the eight mapped levels and `$FCB1` from Pause plus a documented no-cartridge policy for non-input bits. The project API should accept all defined key combinations, including opposing directions, because it describes logical signals rather than a physical controller; refuse unknown mask bits atomically. The cc65 aliases establish A/B bit mapping for project ABI compatibility. The A/B naming crosswalk remains tied to the cc65 aliases. The primary-table follow-up below additionally constrains direction readback by the guest Lefthand bit.

`SWITCHES` also names `CART0_IO_INACTIVE` and `CART1_IO_INACTIVE` at bits 1 and 2 in the pinned cc65 header. They are not logical buttons, and v1 startup tier A has no cartridge input device. Do not expose them through the input setter or assert hardware values for them in the input fixture. Choose one fixed documented tier-A readback policy for these unimplemented cartridge bits; test Pause by its documented bit, and label the remaining bits as policy/unverified.

Represent the Option 2 + Pause combination as two simultaneously held levels. Atari's 1989 Lynx owner manual describes that combination as screen flip/left-handed play, and the cc65 runtime describes a `F` keyboard event for the same chord. Neither source explains whether the screen action is automatic hardware behavior, guest software, or a presentation convention, the automatic chord trigger mechanism. The primary-table follow-up below does document direction remapping through a separate guest Lefthand bit. For this phase, the low-level input API should expose the raw chord and should not silently rotate raw video or reverse direction bits. Treat orientation as an explicitly separate guest/video behavior; record the low-level trigger and direction-remap mechanism as an evidence gap.

## Recommended time contract

- The host owns a canonical, bounded list of `(guest_tick, joystick_levels, pause_level)` records. Ticks are strictly increasing; duplicate-tick updates are coalesced by the host before a run. An omitted initial event means all released; an event at tick 0 is applied after load and before the first advance.
- `lynx_input_set` changes only the current logical levels at the machine's current guest tick. It does not advance time, sample a host clock, discover a controller, retain pointers or invoke callbacks. Validate the full input before applying it. A refusal leaves the instance and tick unchanged.
- For event tick `T > current`, the host calls `lynx_advance(T-current, ...)` and requires exact progress to `T` with a budget stop. When using the frame-stop entry point, handle and copy earlier completed frames, then resume the remaining bounded interval until T; never apply the event early. Undefined/unavailable/error stops abort; watches require an explicit host handling policy rather than silently shifting T. Then set levels at `T` before the next advance. This uses the current half-open API contract: a bus request due at `T` is not started by the advance ending at `T`.
- Sample `$FCB0/$FCB1` at the actual guest CPU bus-read sample tick; the current flat timing model samples at grant tick (`price.sample == 0`). When cycle sampling moves away from the grant in a later timing model, input transitions must be ordered at that sample boundary too. This is deterministic project policy, not a sourced claim about physical button-edge propagation.
- Load/reset returns all logical levels to released. The current levels affect guest-visible reads and therefore belong in snapshot serialization and the guest-state observation digest; bump the snapshot format and preserve validate-before-apply refusal. The unconsumed input script/cursor belongs to the host runner, not the core snapshot. The runner binds the canonical full script hash to `input_digest` and resumes after restore from the first event after the restored tick.
- For a frame endpoint at tick `T`, keep frame data before `T` in the completed output; an event applied at `T` affects later guest reads and later frame content. Avoid putting a timeline event exactly on a frame edge in the first rendering fixture; cover that shared-boundary policy separately after the raw-frame completion contract is frozen.

## Original fixture and independent consumer evidence

Build a project-authored, small tier-A `input_probe` with the pinned cc65 assembler/linker and a BLL header, following the existing `fixtures/diagnostic/first.s` plus manifest pattern. The guest explicitly writes `MAPCTL=$0C` to retain Suzy/Mikey hardware overlays while selecting RAM for ROM/vector spaces before reading `$FCB0/$FCB1`; tier-A load begins with MAPCTL zero. It stores a schema/versioned, progress/error/done result block through named linker symbols. It reads each mapped bit alone, selected combinations, Option 2 + Pause together, and transitions from pressed to released. It must not read the expected host input state or treat the selected CPU profile as guest evidence.

Use an original frame-producing homebrew for the vertical integration slice: configure timer-generated lines/frames and display DMA, poll the logical inputs, and select between two unmistakable pen/palette patterns from the guest. Record a fixed timeline with released, A, B, directional, option, Pause, chord, and release intervals. Keep the chord's raw input behavior separate from the chosen guest-visible pattern; do not claim that a rotated image or direction remap is hardware behavior. Read result and progress symbols from the exact linker labels, and record event ticks, sampled guest values, guest time, frame ticks, raw frame bytes, and the input-script digest separately.

Extend the current public-only consumer path with a dedicated timeline/frame mode rather than replacing the Phase 3 diagnostic path. The current consumer only drives a fixed 5,000-tick diagnostic and emits a labelled P3 snapshot plus placeholder silence; the current runner accepts one tick budget and records the empty-timeline SHA-256. The new consumer should use only the public C API to set levels, advance, stop on frame completion, collect raw frames and write PPM (or PNG if a separate already-approved encoder is selected). Independently parse its output and compare the known fixture pattern, palette/pen values, frame endpoint metadata, and sampled logical input transcript against hand-authored expectations. Same-core output digests establish repeatability only; they do not establish hardware accuracy. Two fresh machines with the same fixture/profile/script should match; changing one input event must change the input transcript and the responsive frame observation. A no-change/all-released control must fail the fixture's specific responsiveness assertion.

## Page-mode, DMA faults, and the pending timer row

The pinned `lynx-tests` source already contains `page-mode/tests.s` (six meaningful result bytes) and `page-mode/main.c` (expected bytes `35 41 69 81 74|75 81`). The current owned `scripts/build-suites.sh` intentionally builds only `cpu` and `timers`; no page-mode runner/skip record exists yet. The assembly body measures Timer 6 around page-mode on/off instruction sequences and a data-read workload; the TGI work is in the upstream C frontend after `_run_tests`. A direct tier-A wrapper that calls the unchanged assembly and writes a guest completion sentinel appears feasible by analogy with the existing timer wrapper, but that is an inference until it is built and run. Plan to run and inventory raw selected-profile observations. O1 blocks a profile compatibility/pass claim, not those observations. If the wrapper or defined tier-A preconditions prevent execution, record `SKIP` with the precise failing dependency and source/build identity; do not use O1 by itself as the blocker.

Phase 4 D-10 remains exactly pending: the pinned timer oracle expects `0D` at result offset 14 while the wrapper observes `0C` on both selected profiles in the provisional flat-five/no-display-DMA path. Revisit the same pinned assembly and unchanged expected byte after the Phase 5 bus/video work, with the initial zero-page counter, MAPCTL/page-mode state, refresh timers, display-DMA enable/cost and wrapper-vs-CRT initialization recorded before comparison. The wrapper currently clears zero page, while the upstream CRT starts display DMA; these are known precondition differences, not proof of the cause. Do not seed the counter to force `0D`, shift timing, change the oracle, or count a pending row as agreement. Preserve the strict mismatch and exact raw row if independent preconditions still do not justify the source value; EVD-02 remains open.

Add the required named DMA fault (`display_dma.cost_zero` or an equally precise missing-cost mutant) and prove a page-mode/timing assertion detects it with a clean positive before and after. Keep it distinct from input-specific faults: `input.a_b_swapped`, `input.option1_option2_swapped`, `input.pause_on_wrong_register`, and `input.edge_applied_one_tick_late` should each fail the bit/sample case they target. Include an unchanged-input/no-run negative control for the homebrew response. Each control needs its intended diagnostic and a fresh positive; compile failure, timeout, absent result or generic nonzero status does not count as a detected behavior fault.

## Adversarial pass and evidence gaps

| Lens | Failure mode to guard against |
|---|---|
| Input/hardware | A/B physical switch crosswalk, unused `SWITCHES` cart bits, pressed polarity and the exact flip/chord mechanism are not fully established by an extracted primary register specification. Keep logical-mask and register-bit claims tied to cc65; label remaining readback policy. |
| CPU/bus | Sampling when a CPU instruction starts rather than when its register read is granted can miss an edge; changing same-tick tie order silently changes results. Exercise event edges at exact and adjacent guest ticks, and record the grant/sample tick. |
| Video | Applying flip to raw frames or rotating the host output can hide whether guest bytes/palette/pen data are correct. Keep raw bytes and host presentation separate; assert exact frame boundaries and avoid first-run edge/frame coincidences. |
| Audio | Input transitions must remain their own guest-tick stream when Phase 6 adds audio; do not make input sampling a host-frame callback that cannot align with audio events. No audio register behavior is required in this phase. |
| Rights/licensing | Use only an original input/homebrew fixture and the pinned cc65 toolchain; no BIOS, commercial ROM or emulator implementation code. The Atari manuals are research sources only and are not copied into fixture/source artifacts. Preserve tool and fixture provenance/notices. |
| Security | Reject unknown bits and malformed/non-monotone/overflowing timeline records before creating outputs; do not retain host pointers; restore current input through validate-then-apply; keep event parsing and file access outside the core. |
| Performance/DevOps | Apply changes only at input edges; do not scan a full event list per master tick or add a dependency. Extend the exact test inventory and source-derived fixture manifest. Keep page-mode as a real run or an explicit blocker-specific skip, never an invisible omission. |

**Remaining evidence gaps:** the AtariAge index exposes the original Handy hardware/programming scans as TIFF images, which the browser could not parse. No readable primary register chapter has yet been verified for active level, exact bus sampling phase, unused switch-line defaults, or flip-control path. The software fixture can close bit-map/determinism regressions but not these hardware gaps. Physical Lynx confirmation remains outside this phase's authority. The `0C`/`0D` timer result remains a separate strict source mismatch until independently justified preconditions produce agreement.

## Primary register follow-up and corrected fixture setup

After the initial handoff, the readable [Epyx hardware-address appendix](https://www.monlynx.de/lynx/hardware.html), sections MAPCTL, SPRSYS, JOYSTICK and SWITCHES, was checked directly. It specifies SPRSYS bit 3 as Lefthand and direction readback dependent on that bit: with Lefthand=1, bits 7/6/5/4 mean Up/Down/Left/Right; with Lefthand=0 they mean Down/Up/Right/Left. The normal orientation is described as Flip off, Lefthand on. This supersedes the initial evidence-gap statement about whether a direction-remap path exists. The input table above describes Lefthand=1. Guest orientation state must be distinct from the host logical mask; cover both values explicitly. No automatic Option2+Pause chord action is inferred. Other SPRSYS sprite/math fields remain unsupported; implementing the input-owned bit must not fabricate active sprite status.

The appendix also supports the eight joystick switch fields, Pause on SWITCHES bit 0, and non-input cartridge bits 1/2; it does not resolve a tier-A disconnected-cartridge electrical value. Keep that readback policy explicit. It states MAPCTL set bits select underlying RAM, so an input fixture must use 0C, not 0F, to keep Suzy/Mikey visible. Use deliberate guest orientation setup (Lefthand=1 for the normal-direction cases), then test the opposite mapping. Exact sampling edges, physical switch polarity and the cc65 A/B naming crosswalk still need their separate evidence labels. No source or timing oracle was altered. This follow-up was reconciled by the parent after the runtime restart; no tests were run.
