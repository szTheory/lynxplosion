## Canonical raw video form, frame boundary, and host contract

| Option | Pros | Cons | Complexity | Recommendation |
|--------|------|------|------------|----------------|
| Packed raw frame packet: 4-bpp pen bytes, 16 palette register pairs per visible line, line/frame tick metadata | Matches VID-03/04, retains original pen and palette observations, small fixed maximum buffers, simple independent renderer | One palette snapshot per line cannot represent intra-line palette changes, exact palette sampling edge remains unverified | Public API + display capture + snapshot v5 + consumer/tests; about 12.3 KB maximum staged frame -- Risk: capture/snapshot state and palette latch assumption | Rec if the phase contract is one raw palette snapshot per line and raster accuracy remains labelled to its evidence |
| Resolved 12-bit color per pixel plus pen and palette sidecars | Host can render the captured raster directly, can preserve palette effects if sampled at each output pixel | Adds a 32,640-byte color plane per maximum frame, freezes a color-word/channel convention, costs more core capture and snapshot bandwidth | Display color sampling, larger output and snapshot schema, consumer conversion; about 45 KB total -- Risk: channel order and unverified pixel sampling behavior | Rec if the phase must preserve palette changes within a line and the source evidence defines the sample point |
| Timestamped line/chunk event records | Naturally reports changing line geometry and palette/timing events, can later refine from line to 16-pixel DMA groups | Variable event counts complicate bounded output capacities and host reconstruction, dropped/backpressured events need explicit recovery, more cursor state | Event queue/API, snapshot continuation and consumer assembly -- Risk: bounded storage exhaustion or skipped events | Rec if raster-event diagnostics become a primary host workflow |

**Rationale:** Recommend the packed raw frame packet for Phase 5 because the accepted requirement explicitly asks for pen data, palette state per line and timing metadata, while the existing public API already uses bounded guest ticks and caller-owned storage. The source-backed geometry is 160 pens × up to 102 visible lines, two 4-bit pens per 80-byte row (8,160 bytes maximum), with three vertical blank lines in the standard 105-line frame; the 16 palette entries can be carried per row as 32 raw bytes in register-address order (`GREEN0..GREEN15, BLUERED0..BLUERED15`), avoiding host-endian or RGB packing in the core. Fixed maximum capacities are 8,160 pen bytes, 3,264 palette bytes and 102 `uint64_t` line-start ticks (816 bytes). Add `line_count`, frame sequence, frame-start tick and frame-complete tick. `line_count` is dynamic from Timer 2 (0–102); rows are emitted in display scan order, without scaling, rotation or color conversion. Define frame completion as the Timer 2 borrow that begins VBlank after the preceding visible scanout; it is guest-time work, not fixed cadence. Expose a new bounded `lynx_advance_frame(max_ticks, buffers, result)` returning the existing `LYNX_STOP_FRAME`; keep the current budget-only `lynx_advance` semantics. Capacity and pairwise/machine-overlap checks happen before progress. A successful frame stop copies once into host buffers and retains no caller pointer; budget or device stops leave those data buffers unchanged, and a refusal leaves the machine and buffers unchanged. Calls retain the existing half-open tick budget: an event exactly at the target is not processed until a later positive budget, and a due event at the current tick may report a frame with zero ticks consumed. The core owns an in-progress capture accumulator, not published caller memory; include its rows/palette/ticks, display DMA and palette cursor, timer/video state, and logical input mask in snapshot format 5 so mid-frame restore produces the same next frame. Successful reset/load clears input and partial capture to the declared power-on state; rejected load/input/restore preserves the full machine and caller buffers. Define a nine-bit logical mask (up/down/left/right/A/B/Option 1/Option 2/Pause); `lynx_set_input` changes the pending mask without advancing time, and subsequent JOYSTICK/SWITCHES reads sample it at the core's declared bus-access sample point. Hosts own the recorded `(guest_tick, mask)` timeline and map physical devices outside the core. To drive an input event at tick T, advance only to the half-open boundary T, handle/copy any earlier frame stops and resume the remaining budget, apply input at T before the next advance, and abort the recording on undefined or unavailable machine stops. The independent consumer should include only `lynxplosion.h`, run the project-authored direct-load homebrew, request complete frames, resolve the documented raw fields to PPM, and compare raw frame plus timing digests across fresh instances; its WAV remains labelled placeholder silence until Phase 6. Meaningful controls are: distinct pen/palette rows with a line-boundary palette change; Timer 0 and Timer 2 changes alter measured line/frame ticks; exact-target and no-frame budget cases preserve output sentinels; input A/B or direction mutations fail the intended homebrew/register assertion; a palette-latch fault fails the palette fixture; a named DMA-cost fault fails its intended page-mode test; and a mid-frame snapshot continuation equals uninterrupted raw output. Keep the Timer 0/2 and palette sampling rules labelled as software policy until independently supported; the Epyx display chapter says the palette is writable at any time, and the pinned lynx-tests timing guide describes palette data sampled during pixel transfer, so per-line snapshots alone do not prove intra-line hardware behavior. The maximum packet is 12,240 bytes plus its small descriptor, a bounded single frame copy with no new dependency; measure the named workload later rather than optimizing speculatively. For DevOps, register exact focused cases in the existing check inventory and keep any unavailable `page-mode` evidence visibly skipped; O1 still blocks a Lynx I/II pass claim. For security and rights, validate output spans before writes, retain no external pointer, use project-authored fixtures, and add no BIOS/game bytes or new package. O9 does not gate this native Lynxplosion API freeze: the read-only LibFuturo tree at `74d0a18` has no Lynx profile, permits `RGB24`/`INDEX8` software video through one caller buffer, and defines `INDEX8` as raw indices with host palette policy, but has no per-line palette or timing sidecar. A later LibFuturo adapter can convert the native frame to the existing `RGB24` profile format; that does not preserve the raw sidecars. If a real LibFuturo consumer must receive pens, per-line palette and ticks, adding those fields/formats is an actual shared-contract change requiring O9 owner approval before it is made. Keep that separate decision for the later adapter phase; no owner decision is needed to complete Phase 5 through Lynxplosion's public C API.
