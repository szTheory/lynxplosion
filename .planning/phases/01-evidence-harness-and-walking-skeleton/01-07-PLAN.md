## Phase Goal (user story)

**As a** developer, **I want to** run one command that builds the core and enforces the rights and determinism boundaries, **so that** I have proof that a skeleton machine is repeatable and refuses bad input without side effects.

<objective>
Add snapshot capture and restore (API-07). Snapshots are a versioned blob with a full identity header. Restore validates every field and the payload hash before it writes anything, then applies in one step that cannot fail. The payload hash uses the SHA-256 unit already proven by `core.sha256` (plan 01-02).

Purpose: Phase 3 needs mid-run snapshot/continue equality, and hosts need refusal guarantees for snapshots from other builds or content.
Output: `core/snapshot.c`, three public functions, and roundtrip and exhaustive-refusal tests.
</objective>

New public functions (exact signatures):
- `lynx_status lynx_snapshot_size(const lynx_machine *m, size_t *size);`
- `lynx_status lynx_snapshot_save(const lynx_machine *m, uint8_t *buf, size_t cap, size_t *written);`
- `lynx_status lynx_snapshot_restore(lynx_machine *m, const uint8_t *buf, size_t len);`

Snapshot layout, format version 1. All integers are little-endian and written field by field, never by `memcpy` of a struct.

Header, in order:
- `magic` 8 bytes `LYNXSNAP`
- `format_version` u32 = 1
- `header_len` u32
- `build_id` 128 bytes: `lynx__build_id`, NUL-padded
- `profile` u32
- `ram_policy` u32
- `ram_seed` u64
- `content_sha256` 32 bytes
- `content_addr` u32
- `content_len` u32
- `payload_len` u32
- `payload_sha256` 32 bytes

Payload, in order: `pc` u16, `a` u8, `x` u8, `y` u8, `s` u8, `p` u8, `halted` u8, `guest_ticks` u64, `ram` 65536 bytes.

Internal constants: `LYNX__SNAPSHOT_MAGIC`, `LYNX__SNAPSHOT_FORMAT 1u`, `LYNX__SNAPSHOT_HEADER_LEN`, `LYNX__SNAPSHOT_PAYLOAD_LEN`, `LYNX__BUILD_ID_FIELD 128u`.
</interfaces>

    - `snapshot_roundtrip`: load the skeleton image (splitmix64, seed `0x0123456789abcdef`), advance 2048, query the size, save (`written == size`), and copy the buffer to `at_save`; advance 2048 more and copy to `final`
    - restore into the same instance → buffer equals `at_save`; advance 2048 → buffer equals `final`
    - a second instance in a fresh buffer with the same config and the same content loaded: restore, then advance 2048 → buffer equals `final`
    - save with `cap = size - 1` returns `LYNX_ERR_CAPACITY` and the output buffer stays all `0xA5`
    - size and save calls leave the instance byte-identical
    - save before any content is loaded returns `LYNX_ERR_STATE`
    - save or restore with a buffer that overlaps the instance memory returns `LYNX_ERR_ARGUMENT`
    - top of the address space: a 16-byte image (no `0xDB`) at `0xFFF0`, advance 28 ticks (7 steps, PC `0xFFF7`), save, advance 36 more and copy to `final_top`; restore into the same instance, advance 36 → buffer equals `final_top` (the restore accepts the high PC and the PC wraps to `0xFFF0` after the sixteenth step)
  </behavior>
  <action>
1. Declare the three functions from `<interfaces>` in `include/lynxplosion.h`. Document that restore accepts only snapshots from the same build, profile, RAM policy, seed and loaded content, and that a refused restore changes nothing. Add them to the signature table in `tests/header/header.c`.

2. Create `core/snapshot.c` and add it to `LYNX_CORE_SOURCES` so both `lynx_core` and `lynx_core_plain` get it. Includes come from the allowlist only. Define static LE put/get helpers per the muhtari pattern.
   - Save checks NULL, magic, has-content, capacity and disjointness of the output buffer from the instance memory (compare `uintptr_t` ranges with the subtraction form) before the first write. It writes the header, then the payload, then computes the payload SHA-256 with `lynx__sha256_*` and writes it into the header. It sets `*written`.
   - Restore validates, in this order, before any write:
     1. NULL/magic → `LYNX_ERR_ARGUMENT` / `LYNX_ERR_STATE`; instance without content → `LYNX_ERR_STATE`; overlap → `LYNX_ERR_ARGUMENT`.
     2. `len` equals the exact snapshot size → else `LYNX_ERR_SNAPSHOT_INVALID`.
     3. magic → INVALID.
     4. version → `LYNX_ERR_SNAPSHOT_VERSION`.
     5. `header_len` → INVALID.
     6. The full 128-byte build id field, including padding, against the instance build's padded id → MISMATCH.
     7. profile, policy, seed, content SHA-256, content address and length against the instance → MISMATCH.
     8. `payload_len` → INVALID.
     9. Recomputed payload SHA-256 → INVALID.
     10. Value ranges, in 32-bit arithmetic: `halted` is 0 or 1; `(uint32_t)pc >= content_addr` and `(uint32_t)pc - content_addr < content_len` → else INVALID. Never compute `content_addr + content_len` in 16 bits.
   - Only then does a single apply step write the fields one by one. It never copies a struct image and never touches padding.
   - Reversibility note for the SUMMARY: restore requires the same build, so no old snapshot is ever accepted, and the format can change in any later build without migration (rated reversible).

3. Add the `snapshot_roundtrip` case per `<behavior>` and register `api.snapshot_roundtrip`. Add the inventory row in sorted order.

## Flagged assumptions (spec-less probe)

- API-07 `unclassified` (status unresolved): covered by the explicit truths above. Two assumptions remain visible. First, sampling the payload every 251 bytes (RESEARCH A4) is enough because the payload hash makes any change detectable. Second, "same build" means an identical build-id string (git revision, dirty flag, compiler and system), so two developers' clean builds of the same commit with the same compiler can exchange snapshots, and a dirty build cannot.
